# Online Novel Search WebApp (なろう小説 拡張検索サイト)





##  プロジェクト概要
**「小説家になろう」の既存機能では不可能な、AND/OR検索を実装した拡張検索ウェブサイトです。**
単なるAPIデータの表示にとどまらず、公式には存在しない検索要件をローカルロジックで補完し、ページネーションやソート時の状態管理を独自に構築することで、ユーザーがストレスなく網羅的に小説を探せるUXの提供を目指しました。

##  使用技術
* **バックエンド・ロジック**: C#14, .NET10
* **フロントエンド・UI**: Blazor (Interactive Server), HTML, CSS, Bootstrap
* **外部連携**: なろうデベロッパーAPI

##  主な技術的課題と「UXを破綻させない」ための解決策

### 課題1：API仕様の壁を越えた「ローカルOR検索」の実装
* **課題**: 公式APIには指定キーワードに対する純粋なOR検索機能が存在しなかった。
* **解決策**: AND検索の条件でAPIからデータを広範に取得し、C#のLINQ（`Where`, `Any`等）を用いてOR検索の条件に合致する小説を自前でフィルタリングする二段構えのロジックを実装。これにより、公式仕様の限界を超えた網羅的な検索を可能にした。

### 課題2：API取得上限（st=2000）に対応する非同期ページネーション
* **課題**: APIの取得開始位置（`st`）に最大2000という制約があり、単純なページネーションでは要件を満たせない問題があった。
* **解決策**: APIから一度で取得できる最大件数のデータをローカルストックにプールし、画面表示用に `Skip` と `Take` で切り出すローカルページネーションを実装。ストックが枯渇した際のみ非同期でAPIから不足分をループで継ぎ足すフェッチ戦略を構築し、APIの制約をクリアしつつ「ページ移行」のUXを標準機能と遜色ないレベルで維持した。

### 課題3：Blazorの非同期ライフサイクルと参照比較の罠の解決
* **課題**: ページネーション実行中に、表示されている小説リストが二重に増幅する複雑な論理バグが発生した。
* **解決策**: デバッグの末、Blazorの非同期処理の割り込み（フライング発火）と、`.ToList()` の仕様による「参照等価性の崩壊」が原因であると特定。純粋な参照比較に基づく状態変更検知変数 （`_isFetchingMore`フラグ等）を導入して状態を正しくリセット・排他制御することで、UIの二重描画を完全に防ぎきった。

##  アーキテクチャと設計思想
* **関心の分離 (Component Design)**: 
  親コンポーネントにAPI通信と全体のオーケストレーションを集約し、子コンポーネントをUIの描画と入力検知（EventCallbackを用いた通知）に特化。これにより保守性と拡張性を大幅に向上させた。
* **状態汚染の防止**: 
  検索条件の生成ロジックにおいて、フィールド変数ではなくローカル変数を用いるよう設計をリファクタリングし、前回の検索条件が残留する「状態汚染バグ」をアーキテクチャレベルで未然に防いだ。
