### プロジェクト概要

- **目的と背景**: 「小説家になろう」の既存機能では不可能な細かいキーワードのAND/OR検索を実現するため。
- **ターゲット**: 小説をより網羅的に検索したいユーザー
- **概要**: なろう小説をAND検索・OR検索両方のアプローチで横断的に検索できるBlazorフレームワークを用いたウェブサイト。

### 使用技術

- **言語/フレームワーク**: C# / Blazor
- **UI/スタイリング**: HTML, CSS, Bootstrap
- **外部API**: なろうAPI

### 技術的課題と解決策

- **課題1：API仕様の壁を越えた「ローカルOR検索」の実装** 
	なろうAPIには指定したキーワードに対する純粋なOR検索機能が存在しなかった。そのため、高優先度（HPC）の条件で広めにAPIからデータを取得し、C#のLINQ（Where, Any等）を用いて、低優先度（LPC）の条件に合致する小説を自前でフィルタリングする二段構えのロジックを実装した。

- **課題2：API取得上限（st=2000）に対応する非同期ページネーション** 
	なろうAPIでは、ページネーションの際に使用する表示開始位置（st）の最大値が2000という制約があり、単純なページネーションではエラーになる問題があった。そこで、APIから取得したデータをローカルにプールし、画面表示用に `Skip` と `Take` で切り出すローカルページネーションを実装。ストックが枯渇した際のみ非同期でAPIから継ぎ足すロジックを構築し、APIの制約とUXを両立させた。

- **課題3：Blazorの非同期ライフサイクルと参照比較のバグ解決** 
	ページネーション中に表示されている小説が二重に増幅するバグが発生。Blazorの非同期処理の割り込みと `ToList()` によるローカルストックのコピーが原因であると特定し、状態変更検知変数を導入して状態を正しくリセットすることで解決した。

### アーキテクチャと設計思想

- **関心の分離**: 親コンポーネントはAPI通信と全体のオーケストレーションを担い、子コンポーネントはUIの描画と入力検知に特化させることで保守性を向上させた。

- **状態汚染の防止**: 検索条件の生成ロジックにおいて、ローカル変数を用いることで状態の管理を厳密化し、前回の検索条件が残る状態汚染のバグを未然に防いだ。
